# Flight Watcher pilot portal: interface contract v1 (FW-0061), revision 3

The interface between Flight Watcher (this app, 1.6.0 and later) and the HOM pilot portal (HOM 1.6.0, a separate,
unprivileged process). Revision 2 (Flight Watcher 1.7.0, HOM 1.8.0) adds tickets on the portal (sections 4 to 7).
Revision 3 (Flight Watcher 1.7.2, HOM 1.8.2) adds two pilot alerts (`bid_calendar`, `schedule_unread`, section 4.3),
the `pilot/set` shape (5.5), refuses `recall/set` from the portal (5.2), adds a pilot's upload of the monthly pairings
package or award (`upload/pdf`, 5.6, with the admin's review outside the portal), the fit alone in the new pairing text
and the manifest's `revision` (4.1). `fwp` and `contract` stay 1, and everything revision 1 and 2 say still holds unless
a section says otherwise. The machine-readable copy is `tests/fixtures/portal_contract_v1.json` (the same name for
revisions 2 and 3), generated by
`portal.contract_text()` from the constants in `roles.py` and `portal.py`; HOM keeps a byte-identical copy at
`fwportal/contract/v1.json`. Both repos pin its sha256 in a test constant (`tests/test_portal_contract.py` here), so a
change to either side's copy fails a test until both are updated together.

| Version | FW release | HOM release | What changed |
|:--|:--|:--|:--|
| contract 1 (`fwp` 1) | 1.6.0 | 1.6.0 | first version |
| contract 1 rev 2 (`fwp` 1) | 1.7.0 | 1.8.0 | tickets on the portal |
| contract 1 rev 3 (`fwp` 1) | 1.7.2 | 1.8.2 | pilot alerts, pilot/set shape, recall/set refused, pilot PDF uploads |

Everything is dark until a pilot entry in the Flight Watcher option `pilots` has `portal: true`. The admin (the
default instance, Ryan's) never has a portal: no folder, no key use, no spool, no export, no ntfy, the same
subscriptions, entities and log lines as 1.5.0. FLICA stays read only: the portal adds no FLICA page loads.

## 1. Folders, owners, modes

| Path | Made by | Owner:group, mode | Written by |
|:--|:--|:--|:--|
| `/share/fw_portal/` | FW `run.py` | root:root 0755 | FW |
| `/share/fw_portal/<name>/` | FW `run.py` | root:2061 0750 | FW |
| `.../<name>/out/`, `out/blobs/`, `out/files/` | FW `run.py` | root:2061 0750 | that pilot's Watcher only |
| `.../<name>/out/*` files | FW | root:2061 0640 | `.<file>.<16 hex>.tmp`, then rename |
| `.../<name>/in/` | FW `run.py` | 2061:2061 0700 | the HOM portal only |
| `.../<name>/in/*` files | portal | 2061:2061 0600 | `.<file>.tmp`, then rename |

- `<name>` matches `roles.NAME_RE` (`^(?=.{1,32}$)[a-z0-9]+(?:_[a-z0-9]+)*$`) and is not reserved (`roles.RESERVED`).
  uid/gid 2061 is reserved for the portal; the Watcher never runs as 2061.
- `run.py` re-applies the modes on every start and refuses (one log line, no portal for that pilot) a folder that is a
  symlink or not a folder. It sets `/share/flight_watcher` to 0700 (root) once any pilot has a portal.
- Portal off is fail-closed (`portal.retire`): on every start, a pilot folder under `/share/fw_portal/` whose pilot
  has no ready portal this start (its entry no longer has `portal: true`, or its key or folders were refused) has its
  `out/` (with `out/blobs/`, `out/files/`) and `in/` emptied, never following a link, with one log line when anything
  went. The folders stay; the portal finds no state.json or manifest.json for that pilot and answers 503. HOM's revoke
  or kill switch is still the immediate cut; removing the folder is optional cleanup. With no `/share/fw_portal/` at
  all nothing is made and nothing is logged.
- Readers skip dotfiles, refuse symlinks (`O_NOFOLLOW` plus `fstat` regular file) and check the owner: the Watcher
  expects uid 2061 on `in/` and its files (when it runs as root), the portal expects root on `out/`.

## 2. Signed envelope (every JSON file under out/)

```json
{"fwp": 1, "kind": "state", "pilot": "demo", "seq": 1763600000123,
 "payload": "<JSON text of the body>", "sig": "<base64url, no padding, 64-byte Ed25519 signature>"}
```

- Exactly these six keys. Signed bytes (UTF-8): `"fwp1\n" + kind + "\n" + pilot + "\n" + str(seq) + "\n" + payload`.
  The payload is a string, so there is no canonical-JSON problem: verify, then parse.
- `kind` is `manifest`, `state`, `events`, `results`, `file:<kind>` or `file:<kind>:<arg>` (section 4.5). The file it
  lives in follows from the kind (`portal.out_name`, `portal.kind_of`): `manifest.json`, `state.json`, `events.json`,
  `results.json`, `files/<kind>.json`, `files/<kind>_<arg>.json`. A reader derives the expected kind from the file it
  opened and refuses a mismatch.
- `seq` is strictly increasing per kind for a pilot: each write takes max(now in ms, last + 1), persisted in
  `<data>/portal_seq.json`, so a clock step back never reorders. The portal keeps the highest seq it served per
  (pilot, kind) and refuses a lower or equal one (rollback).
- Size caps (payload bytes): manifest 256 KB, state 2 MB, events 256 KB, results 64 KB, each file 8 MB, each blob 1 MB
  (`portal.CAPS`). The Watcher does not write a payload over its cap.
- Any failure (signature, `fwp`, keys, pilot, kind, seq, size, owner, symlink): the portal answers 503 for that
  resource and writes an audit row; it never serves unverified bytes.
- An out/ file is written only when its payload changed since the last write of that kind.

## 3. Key handling

- Private key: `/data/portal_ed25519.pem` (PKCS8 PEM, mode 0600, root) in the Flight Watcher container. `run.py` makes
  it before any child starts, and only when some pilot has `portal: true`. One key for the app; the envelope's `pilot`
  binds each file to its pilot. A key file that does not parse moves to `.bad` and a new key is made (logged); the
  portal then answers 503 until HOM's pinned key is updated. A pilot's `watcher.py` only reads the key (never makes or
  moves one). The key is never written under `/share` (`portal.load_key` refuses such a path).
- Public key: `ed25519:<base64url of the raw 32 bytes>` (43 characters after the prefix). `run.py` logs it at every
  start with a portal (`portal signing key ed25519:...`) and the admin's Web UI shows it (Settings, "Pilot portal"). It
  is never written to `/share`.
- HOM pins it in option `fw_signing_key` (schema `match(^ed25519:[A-Za-z0-9_-]{43}$)?`); Node imports it as the JWK
  `{kty: "OKP", crv: "Ed25519", x}`.
- Rotation: a new Flight Watcher key, then Ryan updates the HOM option ([DESTRUCTIVE] Configuration change); the
  portal answers 503 in between.

## 4. out/ files

### 4.1 manifest.json (kind `manifest`)

```json
{"contract": 1, "revision": 3, "app_version": "1.7.2", "pilot": "demo", "prefix": "flight_watcher_demo", "role": "pilot",
 "cards": {"flight-watcher-clock-card-demo.js": "<sha256 hex>"},
 "layout": {"tabs": [{"id": "watcher", "title": "Watcher", "cards": [{"type": "custom:flight-watcher-clock-card-demo"}]}]},
 "services": {
   "switch.flight_watcher_demo_pause": {"toggle": {"sub": "pause/set", "on": "ON", "off": "OFF"},
                                        "turn_on": {"sub": "pause/set", "payload": "ON"},
                                        "turn_off": {"sub": "pause/set", "payload": "OFF"}},
   "button.flight_watcher_demo_check_now": {"press": {"sub": "check_now/press", "payload": "PRESS"}},
   "number.flight_watcher_demo_hunt_check_every": {"set_value": {"sub": "freq/hunt_s/set"}},
   "input_number.flight_watcher_demo_federal_tax_pct": {"set_value": {"sub": "pref/set", "key": "federal_tax_pct"}},
   "input_number.flight_watcher_demo_month_offset": {"set_value": {"local": true}, "increment": {"local": true},
                                                     "decrement": {"local": true}}},
 "mqtt_subs": ["blocked/set", "improved/set", "pilot/set", "recall/act", "settings/set", "trade/set", "upload/pdf"],
 "files": ["finds:2026-11", "pairings:2026-11", "pickers", "pilotver", "recall", "school:2026-27", "versions"],
 "ntfy": false}
```

- Written at start and whenever it changes (a rule added or removed, the list files present, the ntfy setting).
- `revision` (revision 3, Flight Watcher 1.7.2): the contract revision this Watcher speaks (`roles.CONTRACT_REVISION`).
  A manifest without it is revision 2 or older. HOM 1.8.2 refuses a command that came in a later revision than the
  manifest names (`commands.since_revision` in the fixture: `upload/pdf` 3; the ticket commands 2) with a plain
  message, before it reaches the spool ("Your Flight Watcher is too old for this: ask the admin to update it"), and
  takes revision 2 and 3 exports alike.
- `cards`: the pilot's own card copies (`cards.build`, exactly as deployed under `/local/`, except that
  `const FW_PORTAL = false;` reads `true`: `portal.portal_card`) minus the uploads card and the row colors (revision
  2: the tickets card is in), each as `blobs/<sha256>.js` (raw JS, not enveloped). With `FW_PORTAL` on, the settings card sends a
  login sealed or not at all: with no WebCrypto, or before `sensor.<prefix>_settings` in state.json carries
  `pubkey`, Save is disabled and sends nothing (the portal only ever relays ciphertext). The portal serves a blob only
  when its hash is in the verified manifest and re-checks the hash on read. A blob is deleted 1 h
  (`portal.BLOB_KEEP_S`) after the manifest stopped naming it, timed from the Watcher's first sweep that finds it
  unlisted, never from its file time, so a portal still holding the previous manifest (for example across the restart
  of an update that changed a card) can fetch the old card for that hour; a restart starts the hour again.
- `layout`: `portal_layout.json` with the pilot's name: tabs `watcher`, `schedule`, `pilot`, `recall`, `settings`
  and (revision 2) `tickets` last, so the five before it keep their places in the tab bar (`roles.PORTAL_TABS`; the
  portal's tab bar must show all six on a 390 px phone: HOM 1.8.0 wraps it); card types: the pilot's custom cards, `heading`, `tile`, `entity`, `toggle` and static
  `markdown` (text, no templates). Unknown types get a placeholder in the shell.
- `services`: from the discovery entities' command topics (switch `toggle` / `turn_on` / `turn_off` with payloads
  `ON` / `OFF`, button `press` with `PRESS`, number `set_value` with the value as payload), the rule live switches, the
  pref helpers (`pref/set` with their key) and the local helpers (`roles.LOCAL_HELPERS`, view state in the portal,
  never sent). A new entity needs no HOM release.
- `mqtt_subs`: the allowed subs the bundled cards publish directly (`mqtt.publish` to `<prefix>/<sub>`; revision 2:
  also the tickets card's `_pub("<sub>", ...)`, so the five ticket subs; revision 3: the pilot uploads card's
  `upload/pdf`); `drop/set` (admin only), `upload/chunk` and (revision 3) `recall/set` are never one (the recall card
  publishes `recall/set` only from the admin's paste, behind its role check).
- `files`: the list files present in `out/files/` (section 4.5), as `<kind>` or `<kind>:<arg>`.
- `ntfy`: this pilot has a usable ntfy topic (1.6.2: a token is optional, section 6).

### 4.2 state.json (kind `state`)

`{"states": {"<entity_id>": {"state", "attributes", "last_changed", "last_updated"}}, "ha_ok": true}`

- The ids are exactly `watcher.portal_ids()`: the pilot's discovery entities that a portal serves (no uploads
  sensors; revision 2: `sensor.<prefix>_tickets`, his own tickets only, with `answers` and `limits` (section 5.4);
  `sensor.<prefix>_settings` among them), the rule live switches (`switch.<prefix>_rule_<id>_live`)
  and the pref helpers (section 5.3). Never another pilot's or the admin's id, never a house entity.
- Read from Home Assistant one `GET /core/api/states/<id>` per id (a changed state 2 s after its publish, every id
  every 5 min); the pref helpers are synthesized from the pilot's `prefs.json`, never read from HA.
- Masks: `file_key` and `versions_file_key` become 32 zeros (the cards still fetch, and the shim remaps the URL);
  `contact` is removed at any depth; HA's `context` is never copied. `ha_ok` is false when a read failed (the last
  good state of that id is kept).
- Nothing else is masked: state.json is the pilot's own dashboard data, exactly what the pilot's HA dashboard shows.
  It carries crew names, employee numbers and FLICA detail URLs (`sensor.<prefix>_finds` rows' `captain` and
  `picked_by`, `sensor.<prefix>_pickers`, `sensor.<prefix>_pilot_schedule` `emp` and `name`) and the FW-0042 `value`
  and `comm_why` (`sensor.<prefix>_last_new_pairing`, the finds rows); masking them would empty the finds and pickers
  cards. The portal serves state.json only to that pilot's authenticated session.
- Revision 3: `sensor.<prefix>_pilot_uploads`, synthesized by the Watcher (never read from Home Assistant, like the pref
  helpers; the fixture's `synthesized_states`), for the pilot uploads card: `months` (this HST month and the next two,
  each with `pairings` and `award`: `on_file`, `by` ("you", "the admin", "another pilot" or "": never a name) and
  `pending`, his copy waiting for the admin), `mine` (his last 10 uploads: id, kind, month, state, size, at,
  decided_at), `answers` (the last 10: uid, ok, state `receiving`, `checking`, `live`, `pending`, `same` or `error`,
  message, at), `busy`, `receiving` and `limits` (file_bytes, per_day, used_today, left_today, chunk_chars,
  chunk_parts, stale_s, kinds). No file content, no sha256 and no other pilot's upload.

### 4.3 events.json (kind `events`)

`{"events": [{"seq", "ts", "kind", "id", "view", "priority", "title", "body", "data", "tags"}]}`, the last 100.

- Kinds (`roles.PORTAL_EVENTS`, `roles.MACHINE_EVENTS`, `roles.OWN_EVENTS`): `new_pairing`, `rule_match`,
  `recall_miss` (PWA 22.G.2), `request_decided`, `schedule_changed`, `charter`, `hidden`, `needs_settings` /
  `stopped_*` (the Watcher's state turning to one of these; one event per new state), revision 2 `ticket_fixed`, and
  revision 3 `bid_calendar` and `schedule_unread`.
- `bid_calendar` (revision 3, FW-0070): the pilot's own Watcher computes the PBS bid calendar alerts on every instance
  (1.7.1; 08:00 HST the day before the pairing package publishes, 20:00 HST the night before each practice run, 24 h
  before bids close and 20:00 HST the night before they close) and publishes them on its own prefix; from revision 3
  each is a portal event. Its `data` holds only its own fields (`roles.EVENT_KIND_FIELDS`, the fixture's
  `events.kind_fields`): `bid_month`, `alert` (one of `events.bid_calendar_alerts`), `event_hst`, `at_hst`, `source`,
  `cycle_source`; its title and body are the admin's push words, built from those fields alone (`bidcal.alert_text`,
  only dates and what to do), view `watcher`, priority 4. Its `id` is its key with its event time, so a date that moved
  (a package uploaded late) is a new alert.
- `schedule_unread` (revision 3, audit F#3, F#112): the Watcher's own event (never from an MQTT topic): after
  `roles.SCHEDULE_UNREAD_H` (6) hours without a good FLICA schedule read (since the last good read, or since the
  Watcher's start when none came after it), at most once an HST day, not while paused, waiting for the FLICA login or
  stopped (those have their own alert). `data`: `state` (`failing`: reads fail; `waiting`: none could run) and `hours`;
  title "Schedule not read for 7 h", view `schedule`, priority 3.
- `ticket_fixed` (revision 2) is the Watcher's own event, made from the tickets folder, never from an MQTT event topic:
  each move into fixed of one of this pilot's tickets (whoever made it: the admin's instance or Claude's flow; a fix
  later closed still counts, a note does not) that the Watcher has not announced before. The moves of one pass are
  one event (`data`: `ticket`, the id or a list of ids, and `version`, nothing else: never a title or any ticket
  text), title "Ticket FW-0071 fixed in 1.7.0" (or "2 tickets fixed: FW-0071, FW-0072 in 1.7.0"), view `tickets`,
  priority 2 (quiet). The moves already there at its first run, or after `<data>/tickets_fixed_seen.json` is lost, are
  seeded without an event (that file is written even when there is nothing to seed).
- `data` holds only `roles.EVENT_FIELDS`: pairing, dates, start, end, days, month, date, layover, report, release,
  credit, block, fit, far, vac, comm, month_rule, verdict, type, status, added, removed, flight, route, rule_id,
  state, and (revision 2) ticket, version; revision 3 adds a kind's own fields for that kind only (bid_calendar:
  bid_month, alert, event_hst, at_hst, source, cycle_source; schedule_unread: hours). Text values are cut to 120
  characters (40 in a list), control characters go, and a value holding `://` or `@` is dropped. Never `captain`, crew names, employee numbers, `detail_url`, `url`, `contact`, `comm_why` or pay
  amounts (`value`, `pay`): pay and personal commute data never go into events.json or an ntfy push (plan risk K1).
  results.json and manifest.json carry none of them either; state.json and files/ do (sections 4.2 and 4.5).
- `title` and `body` are built from `data` alone (`portal.event_text`), the same text ntfy sends. Revision 3
  (F#161): a new pairing's fit is its value alone ("... Credit 15:20. Fits. FAR 117 OK", or "Conflict ..."), not "Fit
  Fits". `view` is the tab the event opens (`roles.EVENT_VIEWS`); `priority` is 5 for a `new_pairing` that fits the
  schedule and is FAR 117 legal, 4 for `rule_match`, `recall_miss`, `stopped_*` and `bid_calendar`, priority 2 for
  `ticket_fixed`, else 3; `id` is a short hash for dedupe of one
  occurrence, not one pairing: the event's own key or id when it has one, else its `data` plus its own time
  (`since`, `seen`, `at` or `updated`, never in `data`). A replay of the same publish keeps its id; a pairing that
  leaves the pot and comes back, or a rule that matches again later, is a new event with a new id.
- `seq` is strictly increasing and survives a restart (`<data>/portal_seq.json`; the list itself is
  `<data>/portal_events.json`); the portal pages with `after=<seq>`.

### 4.4 results.json (kind `results`)

`{"results": [{"id", "ok", "why"}]}`, the last 50: one per command file that named an id (section 5).

### 4.5 files/ (kind `file:<kind>` or `file:<kind>:<arg>`)

The payload is the list file exactly as the card fetches it. Kinds (`roles.FILE_KINDS`): `finds` (arg `YYYY-MM`),
`pairings` (`YYYY-MM`, the shared package, from two months before this one on), `school` (`YYYY-YY`), `versions`,
`pickers`, `recall`, `pilotver` and (revision 2) `tickets`. No key appears in any name. Copied when the Watcher writes one and on the 5-minute sweep (the
shared pairings packages and the school calendar are written by others); a file that is gone is removed. `tickets` (revision 2)
is `tickets.listing` for this pilot alone (his own tickets, written by his own Watcher into his own folder; the admin's
list of every ticket is in the parent folder under the admin's key and is never read for a pilot): no other pilot's or
the admin's ticket, no history or note text, no photo. Like state.json, these are the pilot's own dashboard data: the finds files keep `captain`,
`picked_by`, `detail_url`, `value` and `comm_why`, and pickers its names and employee numbers. The source folders are in
HA's config folder, which other apps can write, so the Watcher reads a list file only when it is a plain file (no
symlink, FIFO or device: `lstat`, then `O_NOFOLLOW | O_NONBLOCK` and `fstat`, at most the 8 MB cap) in a folder that
is not a symlink; anything else is skipped with one log line and the rest of the pass goes on. A card's `/local/flight-watcher/[<name>/]<kind>_<...>.json` URL maps to
`/fw/api/file/<kind>[/<arg>]` (samples in the fixture, `samples.file_urls`). A kind kept in the pilot's own folder
(every kind but `pairings`) maps only from his folder: the admin's no-folder `/local/flight-watcher/tickets_<key>.json`
and another pilot's folder map to nothing (`samples.file_urls_refused`).

## 5. in/ command files

### 5.1 Format

Name `^\d{13}-[0-9a-f]{16}\.json$` (the ms time and the id), at most 64 KB:

```json
{"fwp": 1, "id": "<16 hex>", "pilot": "demo", "ts": 1763600000123, "sub": "pilot/set",
 "payload": "<exactly what the card would publish>", "session": "<16 hex of sha256(session id)>"}
```

### 5.2 Checks (`portal.Spool`, polled every 1 s, portal pilots only)

The Watcher accepts a file only when: it is a plain file (no symlink, FIFO or folder) owned by uid 2061 (when the
Watcher runs as root) and at most 64 KB (an empty folder is removed; a folder that is not empty is refused once, left
in place and skipped from then on, so it never holds up the commands after it); it is a JSON object with `fwp` 1; `id` is 16 hex and equals the name's;
`pilot` is this pilot; `ts` is at most 300 s old and at most 60 s ahead; `session` is 16 hex; the id was not seen in
the last 600 s (kept across restarts in `<data>/portal_spool.json`); fewer than 30 commands were accepted in the last
minute; `payload` is text; and `sub` is allowed:

`hunt/set`, `pause/set`, `rearm/press`, `check_now/press`, `charter_scan/press`, `freq/normal_min/set`,
`freq/hunt_s/set` (payload a finite number within `roles.FREQ_LIMITS`: `normal_min` 1 to 90 minutes (revision 2; 1 to
20 before), `hunt_s` 5 to 90 seconds, the sliders' ranges; `inf`, `nan` or text is refused), `rule/<id>/live/set` (id `^[a-z0-9_]{1,40}$`),
`blocked/set`, `trade/set`, `pilot/set` (revision 3: its shape, section 5.5), `improved/set`, `recall/act`,
`settings/set` (payload exactly `{"enc": {...}}`, sealed in the browser with the pilot's key from
`sensor.<prefix>_settings`), `pref/set` (section 5.3), (revision 2) `ticket/new`, `ticket/image`, `ticket/act`,
`ticket/edit`, `ticket/delete` (section 5.4) and (revision 3) `upload/pdf` (section 5.6).

Refused, each named in the fixture so a test proves it: `email/alert`, `crew_scan/press`, `upload/chunk`, `drop/set`,
`auto_swap/set`, `swap_map/press`, `hunt/state`, `pause/state`, (revision 3) `recall/set`, `layover/note`,
`upload/decide`, and anything else. `recall/set` left the allowed list in revision 3 (F#78: a crafted paste from the
portal could replace or blank a day on the pilot's own instance): a pilot's recall lists come only from the admin's
Watcher, which forwards each list it takes on MQTT (1.7.1), never through the portal. The admin's own paste on his
Home Assistant dashboard asks for a confirmation naming the dates already on file before it replaces them.

An accepted command is republished as `MQTT <prefix>/<sub>` (qos 1, not retained), so the Watcher's own handler and
its checks run as for a dashboard card. Every file is deleted after reading; a file that named an id gets a result.
A dotfile (the portal's write in progress) is never read and never counts toward a poll's 200-entry cap, so
leftovers cannot hold up the commands after them; it is left alone while fresh, and one not changed for 5 minutes
(`portal.DOT_STALE_S`: a write the portal abandoned between write and rename) is removed, never followed.

### 5.3 pref/set

Payload `{"key", "value"}` (`roles.PREF_KEYS`; checked at the spool and again by the handler):

| key | entity | bounds |
|:--|:--|:--|
| `federal_tax_pct` | `input_number.<prefix>_federal_tax_pct` | 0 to 45 by 0.5 (the schedule card's picker) |
| `state_tax_pct` | `input_number.<prefix>_state_tax_pct` | 0 to 15 by 0.25 (the schedule card's picker) |
| `longevity_year` | `input_number.<prefix>_longevity_year` | 1 to 12 by 1 (PWA 3.B.1; the PWA 3.D.6 table caps at 12) |
| `er_trips` | `input_text.<prefix>_er_trips` | comma list of `+TRIP\|YYYY-MM-DD` / `-TRIP\|YYYY-MM-DD`, at most 255 characters (Extended Range premium, PWA 4.O.1.b) |

The values live only in `<data>/prefs.json` (0600) of that pilot, set by `pref/set`; the HA helpers of a portal pilot
are never read (from 1.6.2: no seed from them, and his pay line reads `prefs.json` alone, a pref not set being the code
default). A value the 1.6.0 seed copied from a never-set helper (at its minimum) is flagged `unconfirmed` once and kept
until a `pref/set` confirms it; the schedule card asks him to set it. The admin never reads a `prefs.json`.
`input_number.<prefix>_month_offset` is view state in the portal (`roles.LOCAL_HELPERS`).

### 5.4 Tickets (revision 2)

A pilot files, sees and acts on his own tickets only, and his Watcher is the authority: the reporter is the
instance, never the payload; the listing, `act`, `edit` and `delete` take his name as `allowed_reporter`, and another
reporter's ticket answers "<id> not found", the same as a missing one. The portal and the spool check only the shape
(`portal.check_ticket` here, HOM's `checkTicket` there), so they can narrow what reaches the Watcher but never widen
it.

- Shapes: `commands.tickets` in the fixture (`roles.TICKET_CMDS`), read as `commands.ticket_rules` says
  (`roles.TICKET_RULES`): the payload is a JSON object whose keys are a subset of `keys` and include `required` (and
  one of `any_of`); `text` lengths are in Unicode code points (Python `len`, JavaScript `[...s].length`) and a
  `pattern` is a full match (Python `re.fullmatch`, JavaScript an anchored RegExp, so a trailing newline is refused);
  every `text` is well-formed Unicode (no lone surrogate: Python `s.encode("utf-8")`, JavaScript `s.isWellFormed()`;
  security review, as Home Assistant's JSON parser refuses one); a one-line field (title, page, version) has the
  `roles.TICKET_LINE_PATTERN` pattern (no control character, no U+2028 or U+2029, no bidi control U+202A to U+202E or
  U+2066 to U+2069) and a text field (narrative, steps, expected, a note) `roles.TICKET_TEXT_PATTERN` (the same but
  tab, line feed and carriage return); ids are ASCII digits (`^FW-[0-9]{4,6}$`);
  `int` is a JSON number with a whole value (2.0 counts as 2; 2.5, `true` and `"2"` do not); `enum` one of `values`;
  `le` pairs and `nonempty_when` as written there. One generic checker on each side, driven by that data, so the two
  cannot drift; every accepted and refused ticket sample in the fixture goes through both.
- `ticket/new` {kind, title, narrative, steps, expected, page, version, cid, images}: never `image` (an inline photo)
  or `reporter`; at most 3 photos.
- `ticket/image` {cid, i, n, part, parts, data}: one chunk of photo `i` of `n`, `part` of `parts` (at most 8), `data`
  a slice of the photo's base64 of at most 60000 characters (no `data:` prefix), so each command stays under the 64 KB
  cap. The portal card reads each photo with `FileReader` into a `data:` URL (the CSP keeps `img-src 'self' data:`, no
  `blob:`), shrinks it in the browser (a long side from 1600 px, JPEG quality 0.82 to 0.52, the size times 0.85 until it
  fits 360000 characters, refused when its short side would fall under 400 px) and sends its chunks in order, one photo
  after the other. The pilot's Watcher (`photos.py`) puts one photo together at a time (the next chunk within 120 s,
  in order; the same chunk twice counts once; a first chunk of another ticket's photo while one is coming is refused),
  then checks the whole base64 strictly, the JPEG or PNG magic bytes and the size, and re-encodes it (Pillow, from a
  fresh image with no info: no EXIF, GPS, XMP, comment, ICC profile, text chunk or trailing bytes, and the saved file
  is walked to prove it; the longest side at most 2048 px) before it stores it in the tickets folder. A photo is
  never served back: not in the export, not in the tickets list.
- `ticket/act` {id, action, text, rid}: `action` one of `roles.PILOT_TICKET_ACTIONS`: `verify` (closes a fixed ticket),
  `reopen`, `note` (with text). `triage`, `progress`, `fixed` and `close` are refused at the spool, at HOM and by the
  Watcher: they belong to whoever works the ticket (the admin's instance and Claude's flow).
- `ticket/edit` {id, rid, title, narrative, steps, expected, page} (at least one field; only while the ticket is new or
  reopened) and `ticket/delete` {id, rid} (security review: only while the ticket is new, so a ticket somebody works
  stays on the admin's list; the folder moves to `tickets/.deleted/`), his own only.
- Quotas, kept by the pilot's Watcher whatever sent the command (`roles.PILOT_TICKET_LIMITS`, the fixture's
  `commands.pilot_ticket_limits`): 10 new tickets in 24 h (deleted ones count), 25 open, 3 photos a ticket, 1.5 MB a
  ticket in all as stored (`ticket_bytes`: its photos and its ticket.json), one photo upload in flight; and (security
  review) `changes_per_day` 30 notes, reopens, verifies and edits in 24 h over all his tickets, `history` 50 of his
  history lines on one ticket, `text_bytes` 256 KB of ticket.json (a verify or a reopen with no text is never refused
  by these three: each follows a fix by whoever works the ticket). A refusal answers "ticket limit reached: ...". The
  admin has none.
- Answers: the pilot's `sensor.<prefix>_tickets` carries `answers`, the last 10 newest first, `{ref, id, action, i,
  ok, error, at}` (`ref` the card's `cid` or `rid`; `i` the photo number), so his card can say "FW-0071 filed", "Not
  filed: ticket limit reached ..." or "Photo 2 not saved: ...", and `limits` (photos, new_per_day, open,
  ticket_bytes). `last` keeps its meaning (the last edit or delete); the admin's sensor has neither.
- The ticket text and photos are a bug report from a third party: untrusted data in every later step (the admin's and
  Claude's fixing flow), never instructions; nothing in a ticket can change the admin's setup.

### 5.5 pilot/set (revision 3)

The pilot lookup (F#49): `commands.shapes["pilot/set"]` in the fixture (`roles.SHAPE_CMDS`), read with the same rules
as the ticket commands (`commands.ticket_rules`; `portal.check_shape` here): keys only `emp`, `q`, `name` and `pick`,
at least one of `emp`, `q` or `pick`; `emp` 1 to 7 ASCII digits; `q` 1 to 60 and `name` 0 to 60 code points of one line
(`roles.PRINTABLE_PATTERN`, the ticket title's: no control character, no U+2028 or U+2029, no bidi control); `pick` 12
lowercase hex (the opaque pick id a name lookup gives). Refused samples are in the fixture. The Watcher refuses the
same on every instance (`watcher.pilot_cmd`), with one log line that never carries the text.

### 5.6 upload/pdf (revision 3, FW-0066)

A pilot uploads the month's pairings package or award PDF from his portal (Ryan, Nov 11: either pilot may upload them;
they are the same document for both). Never the seniority list or the contact list (they hold other pilots' phone
numbers). Shape: `commands.shapes["upload/pdf"]`: every chunk carries `uid` (16 to 40 of `A-Za-z0-9_-`), `kind`
(`pairings` or `award`), `month` (`YYYY-MM`), `size` (1 to 4 MB), `sha` (the file's sha256, 64 lowercase hex), `part`
and `parts` (1 to 94, `part` at most `parts`) and `data` (1 to 60000 base64 characters, no `data:` prefix), so each
command stays under the 64 KB cap. The pilot uploads card (in the bundle, Settings tab) reads the file with
`FileReader` (no `blob:` URL), takes its sha256 with WebCrypto and sends one part every 2.5 s (24 a minute, under the
30 a minute the spool takes, so his other presses still fit; HOM's own rate limits must allow that too). The limits
are the fixture's `commands.pilot_upload_limits` (`roles.PILOT_UPLOAD_LIMITS`): 4 MB a file, 4 uploads a day, one in
flight, 120 s without a chunk drops it, the month this HST month or one of the next two.

The pilot's Watcher (`pilotpdf.py`) checks the whole upload before anything is stored, in the fixture's order
(`commands.pilot_upload_checks`): the chunks in order, the same fields on each, the month and the day's count, the
whole base64 to `size` bytes with sha256 `sha`, `%PDF-` at the start and `%%EOF` in the last 1024 bytes, then its text
from `pdftotext -layout` (the extractor the admin's uploads use) in a child process with a 30 s timeout and memory
(512 MB), CPU (30 s), file size and core limits (`setrlimit` in the child), then the existing parsers: a pairings
package must name that month ("December 2026 Pairing Package"), hold at least 100 pairings (every base and fleet) and
at least one A332 HNL pairing; an award must name that month in its head and hold the pilot's own line (his employee
number from his FLICA schedule). Anything else is refused with a plain reason in `sensor.<prefix>_pilot_uploads`
`answers`; nothing is stored.

- Nothing on file for that month and kind: the upload is used at once (both instances read it as the admin's upload).
- A file on file (the same file again changes nothing): the pilot's copy goes to the quarantine folder
  (`/share/flight_watcher/upload_review/quarantine/`, 0700, files 0600), which no instance reads and nothing serves
  (not the uploads list, not the portal export, not the Web UI), until the admin approves it.
- Provenance per file (who, when, sha256) is kept in `/share/flight_watcher/upload_review/provenance.json`.
- The admin decides outside the portal: his Watcher pushes his phones once per upload (`flight_watcher/event/
  pilot_upload`, an HA automation, time-sensitive: Remove for one used at once, Approve and Reject for one held) and
  takes his answer on `flight_watcher/upload/decide` (`{"id", "action"}`: approve, remove, reject; from the push or his
  Settings uploads card). Approve swaps the held copy in and keeps the replaced file for rollback; Remove takes a
  pilot's file off (the file it replaced comes back when there was one, else nothing is on file) and both instances
  read again; Reject deletes the held copy. `upload/decide` is refused on every portal and is not subscribed by a pilot.

## 6. ntfy

A pilot whose portal is on may save an ntfy topic, and optionally an access token, on its Settings card (sealed only;
the card shows the fields only when `sensor.<prefix>_settings` has `ntfy: true`, and never sends them on the
plain-http fallback). From 1.6.2 a topic only (no token) is allowed: the topic must be at least 24 characters with
both letters and digits (the card generates a 32-character random one), and a topic-only push carries only the kind
in words, the pairing number, the date and the fit (`ntfy.plain_text`; revision 2: for `ticket_fixed` the ticket ids
and the version; revision 3: for `bid_calendar` its admin push words, built from its own fields, only dates and what to
do, and for `schedule_unread` "Schedule not read for 7 h"), with no `Click` header. With a token each portal event goes to the constant
`https://ntfy.sh/<topic>` with `Title`, `Priority`, `Tags`, `Click` (`<fw_portal_origin>/fw/#<view>`, only when the
Flight Watcher option `fw_portal_origin` is a valid `https://<host>.<tailnet>.ts.net` origin) and
`Authorization: Bearer <token>`; the body is the event's body. The manifest's `ntfy` is true with a usable topic,
token or not. Dedupe on
(kind, id), at most 30 pushes an hour, 3 tries with backoff. The token and topic are never logged, urllib3's own
request lines at `log_level: debug` included (a filter on its loggers replaces them with `<hidden>`; installed by the
first ntfy sender, so never on the admin). The admin never posts.

## 7. Versioning

- `fwp` = `contract` = 1. Within 1: new optional fields (readers ignore unknown ones), new file kinds, new layout card
  types (the shell shows a placeholder for an unknown type). Such an additive change is a new `revision` (the
  fixture's top-level `revision`; 2 from Flight Watcher 1.7.0): HOM ships the new fixture first (an allowlist that is a
  superset is safe), then Flight Watcher. The fixture is frozen once HOM's copy is in a pull request.
- A new allowed `sub` changes both allowlists: HOM's pinned copy first (until then the portal answers "not allowed", a
  safe failure), then Flight Watcher.
- Revision 3's rollout: HOM 1.8.2 first (it takes revision 2 and 3 exports and commands, and refuses a revision 3
  command such as `upload/pdf` to a Watcher whose manifest names no revision or revision 2, with a plain message), then
  Flight Watcher 1.7.2; each with the admin's yes, a backup and a 30 min live watch. Rollback is Flight Watcher first
  (1.7.1 refuses `upload/pdf` as "anything else" and still takes `recall/set`, which HOM 1.8.2 no longer sends).
- A breaking change is `fwp` 2: a HOM release that reads 1 and 2, then the Flight Watcher release that writes 2, then a
  HOM release that drops 1.
- The fixture's signed samples use a fixed, labeled test key (`portal.test_key()`: Ed25519 from sha256 of the label
  "Flight Watcher portal contract v1 TEST SEED: not a real key, never used outside tests"; Ed25519 is deterministic),
  never the real key.
