# Flight Watcher pilot portal: interface contract v1 (FW-0061)

The interface between Flight Watcher (this app, 1.6.0 and later) and the HOM pilot portal (HOM 1.6.0, a separate,
unprivileged process). The machine-readable copy is `tests/fixtures/portal_contract_v1.json`, generated by
`portal.contract_text()` from the constants in `roles.py` and `portal.py`; HOM keeps a byte-identical copy at
`fwportal/contract/v1.json`. Both repos pin its sha256 in a test constant (`tests/test_portal_contract.py` here), so a
change to either side's copy fails a test until both are updated together.

| Version | FW release | HOM release | What changed |
|:--|:--|:--|:--|
| contract 1 (`fwp` 1) | 1.6.0 | 1.6.0 | first version |

Everything is dark until a pilot entry in the Flight Watcher option `pilots` has `portal: true`. The admin (the
default instance, Ryan's) never has a portal: no folder, no key use, no spool, no export, no ntfy, the same
subscriptions, entities and log lines as 1.5.0. FLICA stays read only: the portal adds no FLICA page loads.

## 1. Folders, owners, modes

| Path | Made by | Owner:group, mode | Written by |
|:--|:--|:--|:--|
| `/share/fw_portal/` | FW `run.py` | root:root 0755 | FW |
| `/share/fw_portal/<name>/` | FW `run.py` | root:2061 0750 | FW |
| `.../<name>/out/`, `out/blobs/`, `out/files/` | FW `run.py` | root:2061 0750 | that pilot's Watcher only |
| `.../<name>/out/*` files | FW | root:2061 0640 | `.<file>.<16 hex>.tmp`, then rename |
| `.../<name>/in/` | FW `run.py` | 2061:2061 0700 | the HOM portal only |
| `.../<name>/in/*` files | portal | 2061:2061 0600 | `.<file>.tmp`, then rename |

- `<name>` matches `roles.NAME_RE` (`^(?=.{1,32}$)[a-z0-9]+(?:_[a-z0-9]+)*$`) and is not reserved (`roles.RESERVED`).
  uid/gid 2061 is reserved for the portal; the Watcher never runs as 2061.
- `run.py` re-applies the modes on every start and refuses (one log line, no portal for that pilot) a folder that is a
  symlink or not a folder. It sets `/share/flight_watcher` to 0700 (root) once any pilot has a portal.
- Portal off is fail-closed (`portal.retire`): on every start, a pilot folder under `/share/fw_portal/` whose pilot
  has no ready portal this start (its entry no longer has `portal: true`, or its key or folders were refused) has its
  `out/` (with `out/blobs/`, `out/files/`) and `in/` emptied, never following a link, with one log line when anything
  went. The folders stay; the portal finds no state.json or manifest.json for that pilot and answers 503. HOM's revoke
  or kill switch is still the immediate cut; removing the folder is optional cleanup. With no `/share/fw_portal/` at
  all nothing is made and nothing is logged.
- Readers skip dotfiles, refuse symlinks (`O_NOFOLLOW` plus `fstat` regular file) and check the owner: the Watcher
  expects uid 2061 on `in/` and its files (when it runs as root), the portal expects root on `out/`.

## 2. Signed envelope (every JSON file under out/)

```json
{"fwp": 1, "kind": "state", "pilot": "demo", "seq": 1763600000123,
 "payload": "<JSON text of the body>", "sig": "<base64url, no padding, 64-byte Ed25519 signature>"}
```

- Exactly these six keys. Signed bytes (UTF-8): `"fwp1\n" + kind + "\n" + pilot + "\n" + str(seq) + "\n" + payload`.
  The payload is a string, so there is no canonical-JSON problem: verify, then parse.
- `kind` is `manifest`, `state`, `events`, `results`, `file:<kind>` or `file:<kind>:<arg>` (section 4.5). The file it
  lives in follows from the kind (`portal.out_name`, `portal.kind_of`): `manifest.json`, `state.json`, `events.json`,
  `results.json`, `files/<kind>.json`, `files/<kind>_<arg>.json`. A reader derives the expected kind from the file it
  opened and refuses a mismatch.
- `seq` is strictly increasing per kind for a pilot: each write takes max(now in ms, last + 1), persisted in
  `<data>/portal_seq.json`, so a clock step back never reorders. The portal keeps the highest seq it served per
  (pilot, kind) and refuses a lower or equal one (rollback).
- Size caps (payload bytes): manifest 256 KB, state 2 MB, events 256 KB, results 64 KB, each file 8 MB, each blob 1 MB
  (`portal.CAPS`). The Watcher does not write a payload over its cap.
- Any failure (signature, `fwp`, keys, pilot, kind, seq, size, owner, symlink): the portal answers 503 for that
  resource and writes an audit row; it never serves unverified bytes.
- An out/ file is written only when its payload changed since the last write of that kind.

## 3. Key handling

- Private key: `/data/portal_ed25519.pem` (PKCS8 PEM, mode 0600, root) in the Flight Watcher container. `run.py` makes
  it before any child starts, and only when some pilot has `portal: true`. One key for the app; the envelope's `pilot`
  binds each file to its pilot. A key file that does not parse moves to `.bad` and a new key is made (logged); the
  portal then answers 503 until HOM's pinned key is updated. A pilot's `watcher.py` only reads the key (never makes or
  moves one). The key is never written under `/share` (`portal.load_key` refuses such a path).
- Public key: `ed25519:<base64url of the raw 32 bytes>` (43 characters after the prefix). `run.py` logs it at every
  start with a portal (`portal signing key ed25519:...`) and the admin's Web UI shows it (Settings, "Pilot portal"). It
  is never written to `/share`.
- HOM pins it in option `fw_signing_key` (schema `match(^ed25519:[A-Za-z0-9_-]{43}$)?`); Node imports it as the JWK
  `{kty: "OKP", crv: "Ed25519", x}`.
- Rotation: a new Flight Watcher key, then Ryan updates the HOM option ([DESTRUCTIVE] Configuration change); the
  portal answers 503 in between.

## 4. out/ files

### 4.1 manifest.json (kind `manifest`)

```json
{"contract": 1, "app_version": "1.6.0", "pilot": "demo", "prefix": "flight_watcher_demo", "role": "pilot",
 "cards": {"flight-watcher-clock-card-demo.js": "<sha256 hex>"},
 "layout": {"tabs": [{"id": "watcher", "title": "Watcher", "cards": [{"type": "custom:flight-watcher-clock-card-demo"}]}]},
 "services": {
   "switch.flight_watcher_demo_pause": {"toggle": {"sub": "pause/set", "on": "ON", "off": "OFF"},
                                        "turn_on": {"sub": "pause/set", "payload": "ON"},
                                        "turn_off": {"sub": "pause/set", "payload": "OFF"}},
   "button.flight_watcher_demo_check_now": {"press": {"sub": "check_now/press", "payload": "PRESS"}},
   "number.flight_watcher_demo_hunt_check_every": {"set_value": {"sub": "freq/hunt_s/set"}},
   "input_number.flight_watcher_demo_federal_tax_pct": {"set_value": {"sub": "pref/set", "key": "federal_tax_pct"}},
   "input_number.flight_watcher_demo_month_offset": {"set_value": {"local": true}, "increment": {"local": true},
                                                     "decrement": {"local": true}}},
 "mqtt_subs": ["blocked/set", "improved/set", "pilot/set", "recall/act", "recall/set", "settings/set", "trade/set"],
 "files": ["finds:2026-11", "pairings:2026-11", "pickers", "pilotver", "recall", "school:2026-27", "versions"],
 "ntfy": false}
```

- Written at start and whenever it changes (a rule added or removed, the list files present, the ntfy setting).
- `cards`: the pilot's own card copies (`cards.build`, exactly as deployed under `/local/`, except that
  `const FW_PORTAL = false;` reads `true`: `portal.portal_card`) minus the tickets and uploads cards and the row
  colors, each as `blobs/<sha256>.js` (raw JS, not enveloped). With `FW_PORTAL` on, the settings card sends a
  login sealed or not at all: with no WebCrypto, or before `sensor.<prefix>_settings` in state.json carries
  `pubkey`, Save is disabled and sends nothing (the portal only ever relays ciphertext). The portal serves a blob only
  when its hash is in the verified manifest and re-checks the hash on read. A blob is deleted 1 h
  (`portal.BLOB_KEEP_S`) after the manifest stopped naming it, timed from the Watcher's first sweep that finds it
  unlisted, never from its file time, so a portal still holding the previous manifest (for example across the restart
  of an update that changed a card) can fetch the old card for that hour; a restart starts the hour again.
- `layout`: `portal_layout.json` with the pilot's name: tabs `watcher`, `schedule`, `pilot`, `recall`, `settings`
  (`roles.PORTAL_TABS`); card types: the pilot's custom cards, `heading`, `tile`, `entity`, `toggle` and static
  `markdown` (text, no templates). Unknown types get a placeholder in the shell.
- `services`: from the discovery entities' command topics (switch `toggle` / `turn_on` / `turn_off` with payloads
  `ON` / `OFF`, button `press` with `PRESS`, number `set_value` with the value as payload), the rule live switches, the
  pref helpers (`pref/set` with their key) and the local helpers (`roles.LOCAL_HELPERS`, view state in the portal,
  never sent). A new entity needs no HOM release.
- `mqtt_subs`: the allowed subs the bundled cards publish directly (`mqtt.publish` to `<prefix>/<sub>`); `drop/set`
  (admin only) is never one.
- `files`: the list files present in `out/files/` (section 4.5), as `<kind>` or `<kind>:<arg>`.
- `ntfy`: this pilot has a usable ntfy topic and token.

### 4.2 state.json (kind `state`)

`{"states": {"<entity_id>": {"state", "attributes", "last_changed", "last_updated"}}, "ha_ok": true}`

- The ids are exactly `watcher.portal_ids()`: the pilot's discovery entities that a portal serves (no tickets or
  uploads sensors; `sensor.<prefix>_settings` among them), the rule live switches (`switch.<prefix>_rule_<id>_live`)
  and the pref helpers (section 5.3). Never another pilot's or the admin's id, never a house entity.
- Read from Home Assistant one `GET /core/api/states/<id>` per id (a changed state 2 s after its publish, every id
  every 5 min); the pref helpers are synthesized from the pilot's `prefs.json`, never read from HA.
- Masks: `file_key` and `versions_file_key` become 32 zeros (the cards still fetch, and the shim remaps the URL);
  `contact` is removed at any depth; HA's `context` is never copied. `ha_ok` is false when a read failed (the last
  good state of that id is kept).
- Nothing else is masked: state.json is the pilot's own dashboard data, exactly what the pilot's HA dashboard shows.
  It carries crew names, employee numbers and FLICA detail URLs (`sensor.<prefix>_finds` rows' `captain` and
  `picked_by`, `sensor.<prefix>_pickers`, `sensor.<prefix>_pilot_schedule` `emp` and `name`) and the FW-0042 `value`
  and `comm_why` (`sensor.<prefix>_last_new_pairing`, the finds rows); masking them would empty the finds and pickers
  cards. The portal serves state.json only to that pilot's authenticated session.

### 4.3 events.json (kind `events`)

`{"events": [{"seq", "ts", "kind", "id", "view", "priority", "title", "body", "data", "tags"}]}`, the last 100.

- Kinds (`roles.PORTAL_EVENTS`, `roles.MACHINE_EVENTS`): `new_pairing`, `rule_match`, `recall_miss` (PWA 22.G.2),
  `request_decided`, `schedule_changed`, `charter`, `hidden`, and `needs_settings` / `stopped_*` (the Watcher's state
  turning to one of these; one event per new state).
- `data` holds only `roles.EVENT_FIELDS`: pairing, dates, start, end, days, month, date, layover, report, release,
  credit, block, fit, far, vac, comm, month_rule, verdict, type, status, added, removed, flight, route, rule_id,
  state. Text values are cut to 120 characters (40 in a list), control characters go, and a value holding `://` or
  `@` is dropped. Never `captain`, crew names, employee numbers, `detail_url`, `url`, `contact`, `comm_why` or pay
  amounts (`value`, `pay`): pay and personal commute data never go into events.json or an ntfy push (plan risk K1).
  results.json and manifest.json carry none of them either; state.json and files/ do (sections 4.2 and 4.5).
- `title` and `body` are built from `data` alone (`portal.event_text`), the same text ntfy sends. `view` is the tab
  the event opens (`roles.EVENT_VIEWS`); `priority` is 5 for a `new_pairing` that fits the schedule and is FAR 117
  legal, 4 for `rule_match`, `recall_miss` and `stopped_*`, else 3; `id` is a short hash for dedupe of one
  occurrence, not one pairing: the event's own key or id when it has one, else its `data` plus its own time
  (`since`, `seen`, `at` or `updated`, never in `data`). A replay of the same publish keeps its id; a pairing that
  leaves the pot and comes back, or a rule that matches again later, is a new event with a new id.
- `seq` is strictly increasing and survives a restart (`<data>/portal_seq.json`; the list itself is
  `<data>/portal_events.json`); the portal pages with `after=<seq>`.

### 4.4 results.json (kind `results`)

`{"results": [{"id", "ok", "why"}]}`, the last 50: one per command file that named an id (section 5).

### 4.5 files/ (kind `file:<kind>` or `file:<kind>:<arg>`)

The payload is the list file exactly as the card fetches it. Kinds (`roles.FILE_KINDS`): `finds` (arg `YYYY-MM`),
`pairings` (`YYYY-MM`, the shared package, from two months before this one on), `school` (`YYYY-YY`), `versions`,
`pickers`, `recall`, `pilotver`. No key appears in any name. Copied when the Watcher writes one and on the 5-minute sweep (the
shared pairings packages and the school calendar are written by others); a file that is gone is removed. `tickets` is
not exported in contract 1. Like state.json, these are the pilot's own dashboard data: the finds files keep `captain`,
`picked_by`, `detail_url`, `value` and `comm_why`, and pickers its names and employee numbers. The source folders are in
HA's config folder, which other apps can write, so the Watcher reads a list file only when it is a plain file (no
symlink, FIFO or device: `lstat`, then `O_NOFOLLOW | O_NONBLOCK` and `fstat`, at most the 8 MB cap) in a folder that
is not a symlink; anything else is skipped with one log line and the rest of the pass goes on. A card's `/local/flight-watcher/[<name>/]<kind>_<...>.json` URL maps to
`/fw/api/file/<kind>[/<arg>]` (samples in the fixture, `samples.file_urls`).

## 5. in/ command files

### 5.1 Format

Name `^\d{13}-[0-9a-f]{16}\.json$` (the ms time and the id), at most 64 KB:

```json
{"fwp": 1, "id": "<16 hex>", "pilot": "demo", "ts": 1763600000123, "sub": "recall/set",
 "payload": "<exactly what the card would publish>", "session": "<16 hex of sha256(session id)>"}
```

### 5.2 Checks (`portal.Spool`, polled every 1 s, portal pilots only)

The Watcher accepts a file only when: it is a plain file (no symlink, FIFO or folder) owned by uid 2061 (when the
Watcher runs as root) and at most 64 KB (an empty folder is removed; a folder that is not empty is refused once, left
in place and skipped from then on, so it never holds up the commands after it); it is a JSON object with `fwp` 1; `id` is 16 hex and equals the name's;
`pilot` is this pilot; `ts` is at most 300 s old and at most 60 s ahead; `session` is 16 hex; the id was not seen in
the last 600 s (kept across restarts in `<data>/portal_spool.json`); fewer than 30 commands were accepted in the last
minute; `payload` is text; and `sub` is allowed:

`hunt/set`, `pause/set`, `rearm/press`, `check_now/press`, `charter_scan/press`, `freq/normal_min/set`,
`freq/hunt_s/set` (payload a finite number within `roles.FREQ_LIMITS`: `normal_min` 1 to 20 minutes, `hunt_s` 5 to
90 seconds, the sliders' ranges; `inf`, `nan` or text is refused), `rule/<id>/live/set` (id `^[a-z0-9_]{1,40}$`),
`blocked/set`, `trade/set`, `pilot/set`, `improved/set`, `recall/set`, `recall/act`, `settings/set` (payload exactly
`{"enc": {...}}`, sealed in the browser with the pilot's key from `sensor.<prefix>_settings`), `pref/set` (section
5.3).

Refused, each named in the fixture so a test proves it: `email/alert`, `crew_scan/press`, `ticket/new`,
`ticket/image`, `ticket/act`, `ticket/edit`, `ticket/delete`, `upload/chunk`, `drop/set`, `auto_swap/set`,
`swap_map/press`, `hunt/state`, `pause/state`, and anything else.

An accepted command is republished as `MQTT <prefix>/<sub>` (qos 1, not retained), so the Watcher's own handler and
its checks run as for a dashboard card. Every file is deleted after reading; a file that named an id gets a result.
A dotfile (the portal's write in progress) is never read and never counts toward a poll's 200-entry cap, so
leftovers cannot hold up the commands after them; it is left alone while fresh, and one not changed for 5 minutes
(`portal.DOT_STALE_S`: a write the portal abandoned between write and rename) is removed, never followed.

### 5.3 pref/set

Payload `{"key", "value"}` (`roles.PREF_KEYS`; checked at the spool and again by the handler):

| key | entity | bounds |
|:--|:--|:--|
| `federal_tax_pct` | `input_number.<prefix>_federal_tax_pct` | 0 to 45 by 0.5 (the schedule card's picker) |
| `state_tax_pct` | `input_number.<prefix>_state_tax_pct` | 0 to 15 by 0.25 (the schedule card's picker) |
| `longevity_year` | `input_number.<prefix>_longevity_year` | 1 to 12 by 1 (PWA 3.B.1; the PWA 3.D.6 table caps at 12) |
| `er_trips` | `input_text.<prefix>_er_trips` | comma list of `+TRIP\|YYYY-MM-DD` / `-TRIP\|YYYY-MM-DD`, at most 255 characters (Extended Range premium, PWA 4.O.1.b) |

The values live in `<data>/prefs.json` (0600) of that pilot. It is seeded once from the HA helpers: at the first start
with a portal, or, when Home Assistant does not answer for every helper then (down, a 5xx, a helper `unavailable`
or a number helper still `unknown`), on the first 5-minute export sweep that it does. A helper HA answers 404 for
has nothing to seed; `input_text.<prefix>_er_trips` reading `unknown` (an input_text that was never set stays
`unknown` for good) seeds as empty (no ER trips); a value `pref/set` saved before the seed is kept. The Watcher's own pay line reads it before the helpers (`tax_pct`, `pay_settings`); the admin never
reads a `prefs.json`. `input_number.<prefix>_month_offset` is view state in the portal (`roles.LOCAL_HELPERS`).

## 6. ntfy

A pilot whose portal is on may save an ntfy topic and access token on its Settings card (sealed only; the card shows
the fields only when `sensor.<prefix>_settings` has `ntfy: true`, and never sends them on the plain-http fallback).
Each portal event then goes to the constant `https://ntfy.sh/<topic>` with `Title`, `Priority`, `Tags`, `Click`
(`<fw_portal_origin>/fw/#<view>`, only when the Flight Watcher option `fw_portal_origin` is a valid
`https://<host>.<tailnet>.ts.net` origin) and `Authorization: Bearer <token>`; the body is the event's body. Dedupe on
(kind, id), at most 30 pushes an hour, 3 tries with backoff. The token and topic are never logged, urllib3's own
request lines at `log_level: debug` included (a filter on its loggers replaces them with `<hidden>`; installed by the
first ntfy sender, so never on the admin). The admin never posts.

## 7. Versioning

- `fwp` = `contract` = 1. Within 1: new optional fields (readers ignore unknown ones), new file kinds, new layout card
  types (the shell shows a placeholder for an unknown type).
- A new allowed `sub` changes both allowlists: HOM's pinned copy first (until then the portal answers "not allowed", a
  safe failure), then Flight Watcher.
- A breaking change is `fwp` 2: a HOM release that reads 1 and 2, then the Flight Watcher release that writes 2, then a
  HOM release that drops 1.
- The fixture's signed samples use a fixed, labeled test key (`portal.test_key()`: Ed25519 from sha256 of the label
  "Flight Watcher portal contract v1 TEST SEED: not a real key, never used outside tests"; Ed25519 is deterministic),
  never the real key.
